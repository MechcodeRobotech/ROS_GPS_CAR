# Handing this project to a Claude session on Windows

Paste the block below into Claude Code on the Windows machine. Everything above
it is for the person doing the handing over.

## What this is for

The Ubuntu machine cannot test Windows. It can build for it, reason about it and
push files to the share, but it cannot run PowerShell, cannot see the Windows
firewall, and cannot tell whether Docker Desktop's networking behaves the way
the documentation claims. Those questions need a Windows session, and that
session needs to arrive knowing what is already true so it does not re-derive
it or, worse, "fix" something that is deliberate.

Every claim in the prompt below was established on the Linux side, most of them
by something breaking first. They are context, not instructions.

## Before handing over

```bash
tools/sync_windows.sh push        # this machine -> the share
```

Then on Windows, once, as administrator:

```powershell
powershell -ExecutionPolicy Bypass -File setup\setup_windows.ps1
```

That opens TCP 8080 and UDP 8888 and warns if the network profile is Public,
where Private and Domain firewall rules do not apply at all. Without it the
symptom is precise and misleading: the container is healthy, the UI works
locally, the robot never connects, and nothing appears in any log - because
Windows Firewall drops the inbound packets before Docker ever sees them.

## When Windows is done

```bash
tools/sync_windows.sh pull        # share -> _work/, NOT the real tree
tools/sync_windows.sh report      # the test report from the Windows run
```

A pull lands in `_work/` on purpose. Anything edited on Windows is unreviewed
and untested here, and putting it straight onto the real tree would let changes
into git without QC seeing them.

## The prompt

> You are working on GPS_Localize on a Windows machine. The project was
> developed on Ubuntu and this session exists to test and fix the Windows half.
>
> **What you are here to do**
>
> Run `test_windows.bat` and fix what it finds. Report anything the machine
> cannot do as SKIP - never as a pass. A skipped check that reads as green is
> worse than a failing one, because nobody goes back to it.
>
> **Read `CLAUDE.md` in the project root first.** It carries the working rules,
> including the one that matters most here: after changing anything, sweep the
> repository for everything that pointed at what changed. Documentation that
> disagrees with the code is worse than no documentation, because it is
> believed.
>
> **What is already known, so you do not re-derive it**
>
> - `network_mode: host` is Linux-only. On Docker Desktop the container runs in
>   a VM, so "host" is that VM and not the PC, and the ESP32 can never reach the
>   agent. `docker-compose.windows.yml` publishes 8080/tcp and 8888/udp instead.
>   Every node and the agent live in one container, so DDS never crosses the
>   boundary and publishing those two ports is enough.
> - `devices: []` does NOT clear a device list - Compose merges sequences. Only
>   `devices: !reset []` removes one. A device that does not exist stops the
>   container from starting at all, which is why the base compose file lists
>   none: `/dev/ttyUSB0` does not exist unless a board happens to be plugged in,
>   and that is the normal case.
> - The Windows viewer once reported `No module named 'configstore'` when the
>   real problem was that **pyyaml was not installed**. A broad `except
>   ImportError` swallowed the missing third-party dependency and fell through
>   to the frozen-build path, which then failed on a different name entirely.
>   Fixed, but the shape of that bug is worth remembering: an import guard that
>   catches too much turns a clear error into a confusing one.
> - `ROS_DOMAIN_ID` is **10** and must match on both sides. A mismatch shows an
>   empty topic list and no error whatsoever.
> - The repository is **private**, so the documented one-line installer
>   (`curl … | bash`) returns 404 for anyone unauthenticated. Clone with `gh` or
>   pass a token. Verified in a clean container.
> - A checkout COPIED from another machine carries `build/` and `install/` with
>   absolute paths from wherever it was made, and colcon then fails with
>   "CMakeCache.txt directory is different than", naming a path that does not
>   exist. `setup/install.sh` detects and clears only genuinely foreign caches.
>   **This applies to you**: a tree that arrived over the share is exactly that
>   case.
>
> **How to check your work**
>
> ```
> python tools\qc.py
> python tools\port_qc.py --static-only .
> ```
>
> Both must pass before anything is pushed back. There are also host tests
> (`pio test -e native`) if PlatformIO is installed; skip them if it is not,
> and say so.
>
> **What NOT to do**
>
> - Do not edit `plan.html` by hand - it is generated by `tools/planhtml.py`.
> - Do not edit the `workspace`, `firmware` or `docker` branches. They are
>   generated from `main` by `tools/publish_branches.sh`, and a hand edit is
>   overwritten the next time it runs.
> - Do not commit `firmware/config/network_secrets.h`. It is gitignored and
>   holds real Wi-Fi passwords.
> - Do not "fix" the absence of `/dev/ttyUSB0`. On Windows the serial port is
>   `COM<n>`, and the code already handles both.
>
> When you are done, leave the changes in place and say what you changed and
> what you could not test. The Ubuntu side pulls them into `_work/`, runs QC,
> and promotes them as a separate decision.
